# Spec Delta

## Purpose

让 Plan 模式把 Agent 负责的开发工作与用户负责的验收工作拆成两条互不干扰的进度线：开发进度由 Agent 上报并驱动完成判定，验收进度只由用户手动勾选，因此一次执行可以在开发完成时结束，而不把人工验收伪装成已完成、也不因它而卡死。

## ADDED Requirements

### Requirement: 计划文档把用户验收与开发任务分成两个章节

Plan 文档 SHALL 用两个互不重叠的顶层章节表达两类工作。`## Tasks` MUST 只包含 Agent 自己可以完成的编码、测试与可执行检查，其中任何任务的 `verify:` 条件 MUST NOT 要求用户手工确认。`## Acceptance` SHALL 位于 `## Verification` 之后，内容为未勾选的 Markdown checklist，每条 SHALL 同时写明具体操作与预期结果。

#### Scenario: 新生成的计划把两类工作分列

- **WHEN** Dext 为一个新计划组装默认 Plan 指令
- **THEN** 文档骨架按 `## Tasks`、`## Verification`、`## Acceptance`、`## Risks` 的顺序列出章节
- **AND** 验收指引要求使用未勾选 checklist，每条写明具体操作与预期结果，并明确禁止“检查是否正常”这类空泛表述
- **AND** 任务规则说明 `## Tasks` 及其 `verify:` 只覆盖 Agent 工作，用户验收一律写在 `## Acceptance`

#### Scenario: 验收项不会混入开发任务

- **WHEN** 计划文档的 `## Tasks` 有三条任务，`## Acceptance` 有三条 checklist 条目
- **THEN** 解析出的开发任务恰好是这三条任务，编号为 `plan-1` 到 `plan-3`
- **AND** 解析出的验收项恰好是这三条条目，按文档顺序排列，全部未勾选，且没有任何一条带 `plan-*` 形式的 ID

#### Scenario: 验收只接受条目行的写法

- **WHEN** `## Acceptance` 中使用 `- [ ]`、`* [x]` 或 `1. [ ]` 写条目
- **THEN** 三种写法都会被解析为验收项，初始勾选状态取自方括号内的字符
- **AND** 围栏代码块里出现的 checklist 行不会被解析，其他章节的 checklist 也不会被当作验收项

#### Scenario: 没有验收章节的旧计划保持兼容

- **WHEN** 计划文档完全没有 `## Acceptance` 章节
- **THEN** 它的验收列表为空，Todo 面板不显示验收组
- **AND** 执行、续跑、恢复与完成判定与改动前完全一致，不需要迁移或改写计划文件

### Requirement: 验收项的身份由归一化文本派生

验收项 SHALL 拥有由归一化文本派生的确定性 ID——去除首尾空白、折叠内部空白并忽略大小写——而不是由数组位置派生。把已保存的验收状态套用到变化后的清单时，MUST NOT 把勾选状态转移到另一条文本不同的条目上。

#### Scenario: 重排与插入保留已有勾选

- **WHEN** 已保存的验收列表是 `[A 已勾选, B 未勾选]`，修订后的文档列出 `[C 新增, B, A]`
- **THEN** 合并后的状态是 `[C 未勾选, B 未勾选, A 已勾选]`

#### Scenario: 改写条目不继承旧勾选

- **WHEN** 一条已勾选的验收项在计划中的文本被改写
- **THEN** 改写后的条目显示为未勾选，因为它的 ID 已改变

#### Scenario: 文本相同的条目各自独立

- **WHEN** 两条验收项的文本完全相同
- **THEN** 它们获得互不相同的 ID，可以各自独立勾选，互不影响

### Requirement: Todo 面板分别统计开发任务与用户验收

Todo 面板 SHALL 在开发任务组下方展示一个验收组，两组使用各自的计数；验收项 MUST NOT 计入开发任务的分母。验收组 SHALL 保持可见而不默认折叠，每条验收项 SHALL 提供一个带标签关联的原生复选框，且只有用户交互才能改变其状态。

#### Scenario: 两组独立计数

- **WHEN** 17 条开发任务全部完成，3 条验收项一条都未勾选
- **THEN** 开发组显示 `17/17` 并表明 Agent 工作已完成
- **AND** 验收组显示 `0/3`，并逐条列出可勾选的验收项

#### Scenario: Agent 上报无法改变验收状态

- **WHEN** Agent 发出任意 `dext-todo` 上报，包括一条刻意使用验收项 ID 的上报
- **THEN** 每个验收复选框都保持当前状态
- **AND** 该条上报按现有规则被整条丢弃，因此同一份上报里的开发任务更新也不会生效

#### Scenario: 只有用户点击能改变验收

- **WHEN** 用户点击某个验收复选框
- **THEN** Webview 针对该计划路径与条目 ID 发送 `togglePlanAcceptance` 请求
- **AND** 宿主校验通过后持久化新状态，并以宿主状态重新渲染验收组，焦点回到被切换的那个复选框

#### Scenario: 宿主拒绝不匹配的勾选请求

- **WHEN** 请求里的计划路径与会话当前的 `planProgress.path` 不一致，或条目 ID 不在该计划的验收列表里
- **THEN** 宿主拒绝该请求，验收状态保持不变，也不写入任何进度

### Requirement: 验收状态随会话持久化

验收状态 SHALL 存放在会话既有的 `planProgress` 记录中，并使用既有的 `updatePlanProgress` 写入路径，因此 Webview 重载、切换会话或扩展重启后仍然保留。仅更新开发任务进度时 MUST NOT 清除已保存的验收状态。

#### Scenario: 重载后状态仍在

- **WHEN** 用户勾选两条验收项，然后重载 Webview 并重新打开该会话
- **THEN** 这两条仍然是勾选状态，计数显示为 `2/3`

#### Scenario: 开发进度写入不抹掉验收

- **WHEN** 计划执行过程中宿主只写入新的开发任务进度，且不携带验收列表
- **THEN** 该会话此前保存的验收状态原样保留

#### Scenario: 其他会话不受影响

- **WHEN** 一个会话的验收状态被更新
- **THEN** 另一个会话的验收列表与勾选状态保持不变

#### Scenario: 计划完成后仍可勾选

- **WHEN** 开发任务已全部完成并且执行已结束时，用户勾选一条验收项
- **THEN** 该勾选被接受并持久化，因为校验依据是 `planProgress.path` 而不是在完成时被清除的活动计划路径

### Requirement: 执行是否结束只取决于开发工作

一次 Plan 执行 SHALL 在每条开发任务都上报完成、且 Agent 的最终验证通过时自动结束，与是否还有未勾选的验收项无关。未勾选的验收项 MUST NOT 产生 `blocked` 结果，也 MUST NOT 触发任何续跑轮次。

#### Scenario: 待验收不阻断也不续跑

- **WHEN** 每条开发任务都已完成，最终验证通过，仍有两条验收项未勾选
- **THEN** 该轮以 `completed` 结束，不再请求下一轮
- **AND** 回合标签显示“已完成 · 待用户验收”

#### Scenario: 验收全部勾选后的标签

- **WHEN** 用户勾选最后一条剩余验收项
- **THEN** 该回合标签显示“已完成 · 验收完成”

#### Scenario: 未完成或失败的 Agent 工作仍然算失败

- **WHEN** 仍有开发任务未完成，或最终验证未通过，或 Agent 为自己的工作报告了外部阻塞
- **THEN** 现有的 `incomplete` / `blocked` 处理保持不变
- **AND** 验收状态永远不能把一次失败的检查变成完成

#### Scenario: 无法用验收掩盖未完成的工作

- **WHEN** 计划的执行结果不是 `completed`，而对话框中存在未勾选的验收项
- **THEN** 标签不会显示“待用户验收”，也不会把未实现的任务或失败的检查表述为待用户验收的事项

### Requirement: 最终回复分开陈述开发结果与待验收内容

Plan 执行指令 SHALL 要求最终回复先说明实现了什么、哪些自动检查通过，再列出仍需用户亲自执行的验收步骤，并 MUST NOT 通过任务协议上报任何验收项。

#### Scenario: 回复结构

- **WHEN** Agent 在仍有未勾选验收项的情况下结束一次 Plan 执行
- **THEN** 指令要求它先报告开发内容与通过的自动检查
- **AND** 随后列出待用户执行的验收步骤，且不把任何验收项作为开发任务或 `dext-todo` 上报
