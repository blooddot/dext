# 发布说明（release/notes）

把 `since...HEAD` 的用户可见变化整理成发布页面可用的发布说明。只读：不写 CHANGELOG，不改代码，不打包。

## 输入

- `git diff --stat` 与 `git diff` 全文：本次发布相对起点的全部改动。
- `CHANGELOG.md` 的本版段落原文；可能缺失。
- 版本号、项目名与日期由调用方给出，你只产出内容。

## 与 CHANGELOG 的关系

- CHANGELOG 本版段落是主要来源：它已经过分类与去重，发布说明在它基础上改写，不必重新逐条读 diff。
- CHANGELOG 缺失时只依据 diff 整理。
- 两者冲突时以 diff 为准，并在 `problems` 里写明哪条不一致。
- 发布说明比 CHANGELOG 短：CHANGELOG 保留全部用户可见条目，发布说明只留升级者最需要知道的部分。

## 分类

每条候选内容只归一类，按下面的顺序判断：

1. **highlights**：本版最值得知道的 1-3 条结论（最重要的功能、最大的破坏性改动）。
2. **breaking**：会打断既有用法的移除或语义变化，每项含 `change` 与 `migration`。
3. **features**：净新增且用户可感知的能力。
4. **fixes**：修好的用户可感知缺陷。
5. **notes**：其他用户可感知的影响，例如性能、兼容性、已知问题。

过程条目（本版加了又删、改了又改回去）一律不写；内部重构、变量改名、测试改动与依赖小版本升级也不写。

## 写法

- 用英文，与 `CHANGELOG.md` 现有条目一致。
- 面向升级者：说清楚什么变了、对他有什么影响、要不要动手。
- 每条一行，动宾结构，必要时用反引号给出标识符、配置键或路径。
- 条目不要带 `- ` 前缀，也不要带版本号、日期或 `##` 标题；调用方负责渲染列表。
- `migration` 必须是可执行的替换动作：改哪个文件或配置键、改成什么、改完是什么样。
- 只写 diff 或 CHANGELOG 能证明的内容；没有证据就不写，也不要为了凑满小节编造。
- 同一变化只出现一次；每节最多 12 条。

## 输出契约

只输出一个 JSON 对象，不要代码围栏、解释或前后缀。字段固定为下面七个，缺一不可：

- `summary`：字符串，2-4 句，说明本版最重要的事。
- `highlights`：字符串数组，最多 3 条。
- `breaking`：对象数组，每项有 `change`（变化本身）与 `migration`（迁移动作）；写不出迁移动作的不要放进这里。
- `features`：字符串数组。
- `fixes`：字符串数组。
- `notes`：字符串数组。
- `problems`：字符串数组；只在无法完成整理时填写（例如 diff 读不出、CHANGELOG 与 diff 矛盾）。非空会让调用方标记这份发布说明需要人工补正。

没有内容的数组给空数组，不要省略键。
