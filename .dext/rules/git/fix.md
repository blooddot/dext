# 修复代码审查发现的问题

当本规则被加载到一次 Agent 调用中时，只修复任务输入里点到的问题。

## 范围

- 输入可能是完整审查报告、一条发现，或一句自定义的修复要求。
- 有严重性小节（Critical / High / Medium / Low / Suggestion）时，只改 `Critical` 与 `High`；其余条目只写进报告，不动代码。
- 没有严重性标签的条目按主题处理：能对应到具体代码缺陷就修，判断不了就降到「只列出」。
- 输入之外一律不碰：不顺手修 Low、不重构、不格式化、不删死代码。

## 边界

- 不碰 `openspec/`：不改 `tasks.md`、`spec.md`，不跑 `openspec` 命令。
- 要改某个 `spec.md` 里的 Requirement 才修得好时，停下来报告，交给 `spec.update`。
- 不提交、不推送、不 amend、不改版本号。

## 定位

1. 有 `path:line` 时先读那段代码确认问题能复现；只有口头描述时（"导出按钮点两次会崩"）先定位：从报错信息或复现步骤反推调用链，找到最能解释现象的那一处，不要从看起来可疑的相邻代码下手。
2. 用 grep 找出被改函数的每一处调用方。根因在共享函数里就改共享函数一次，不在调用点打补丁。
3. 能先写一个失败的测试就写，再改到通过；写不出测试的，说明为什么。

## 验证

- 跑改动对应的测试；没有可跑测试时，至少跑项目门禁（本仓库 `npm run check`）。
- 跑不过不许报「已修复」，把失败输出原样贴出来。

## 输出

- 逐条对照表：`路径:行` → 改了什么 → 已修复 / 已跳过（原因）。
- 根因，以及为什么改这里而不是调用点。
- 跑过的命令与结果，以及仍需人工确认的部分。
- 如果某条其实是 spec 缺口而不是实现 bug，明确说出来。
