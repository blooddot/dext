# 文档漂移审计

只读审计阶段：对照当前代码检查 `docs/`，产出可执行的改动清单。此阶段不修改任何文件。

## 输入

- 用户请求可能限定范围（某个功能、某个页面、某个目录）。未限定时审计整个 `docs/`。
- 以代码为准：`package.json`（脚本、命令、配置项、视图与设置）、`src/**`（模块、入口、对外行为）、`README.md` 与 `README.zh-CN.md`（对外承诺）。

## 审计方法

1. 列出 `docs/**/*.md`，按文件名建立中英配对：`<name>.md` 与 `<name>.zh-CN.md`。只有单侧的页面单独标注。
2. 逐个页面提取它描述的能力：命令、配置项、界面流程、模块名、返回类型、限制、默认值。
3. 在代码中定位每条断言的依据。找不到依据的断言标为 unverified，不要假定它正确。
4. 找出代码已有、文档未覆盖的对外能力：新增的脚本与命令、设置项、CLI 后端、MCP 传输、Plan 行为、公开 API 与结果类型。
5. 找出只有一侧语言更新的页面：比较两版的章节标题与代码块数量，标题或示例数量不一致即为漂移。

## 输出格式

严格按以下小节输出，不写引言和结尾。

### 范围

一句话说明本次覆盖的页面与代码区域。

### 页面状态

表格，列为：页面、语言配对（完整/单侧）、结论（current/stale/partial）、证据。

### 漂移项

逐条列出，每条包含：页面、位置（章节或行号）、文档当前说法、代码中的事实、证据路径（`path:line`）、建议动作（修改/删除/新增段落）。

### 缺失页面

代码已有但 `docs/` 无对应页面的能力：建议页面名、目标读者、必须覆盖的要点、证据路径。

### 待验证

无法从代码确认的断言，写明页面与原因。没有则写“无”。

## 约束

- 只读：不写文件、不应用补丁。
- 每条结论都要能指向具体文件与行；指向不了的结论不要写。
- 不评价文笔，只报告与代码不一致、缺失、配对不完整三类问题。
- 相同原因的多个页面合并成一条，输出保持紧凑。
